Scene-Specific Ambiguity-Aware 3D Language Fields

SaaF — towards interactive real-world object retrieval

Yuga Yano1,2, Daiju Kanaoka2, Hakaru Tamukoh2,3, Yasutomo Kawanishi2

1 Kyushu Institute of Technology · 2 RIKEN · 3 RIKEN Center for Neuromorphic AI Hardware

A service robot should be able to act on a sentence like “bring me the tart”. To do that it needs a memory of the room that is both spatial, so an object can be found and reached, and linguistic, so a phrase can be matched against it. A 3D language field is exactly that memory: a reconstructed 3D scene in which every point also carries a language vector.

SaaF is a 3D language field that adds two properties to the usual design. First, its feature space is trained to keep visually similar objects apart. Second, the same space is trained so that vague phrases land near the origin, which turns the length of a query vector into a measurement of ambiguity. When that measurement says a request is unclear, the system asks which object you meant instead of guessing.

Abstract & scope

Summary

SaaF is a Gaussian-Splatting based 3D language field for interactive object retrieval in a single real-world scene. Existing methods, most directly LangSplat, embed autoencoder-compressed CLIP features into the Gaussians, but the autoencoder is trained only to reconstruct, not to separate. Two failures follow: visually similar instances blur together after compression, and ambiguous queries such as “the bottle” in a room with three bottles still receive a confident best guess.

SaaF changes the training objective rather than the architecture. A metric-learning term pulls multiple views of one object together and pushes different objects apart; a VLM-generated label set per object, spanning unique names to supercategories, teaches the space where vague concepts belong. Both changes act on one shared feature space, and the result is a space where direction encodes identity and length encodes ambiguity. Retrieval then asks a single question — is the query vector’s norm below a threshold μ — before deciding whether to retrieve or to ask the user.

On the 3D-OVS dataset, SaaF reaches 96.4 overall IoU against LangSplat’s 93.5, leads every scene including the sofa scene with two similar controllers (95.7 vs 90.0), retrieves in 6.3 ms against 9.6 ms, and separates ambiguous from unambiguous queries using the norm alone.

1 The problem

This chapter sets up the exact task and shows why ambiguity is a property of the scene, not just of the sentence. It ends with four requirements that a retrieval system has to satisfy, and the rest of the report checks them one by one.

1.1 Ambiguity lives in the scene

“Bring me the bottle” is only ambiguous if the room actually holds several bottles. The same words are perfectly clear in a room with one. A robot therefore cannot judge a request from the sentence alone; it has to compare the words against the objects that exist in this particular reconstructed room. That makes ambiguity a scene-specific, measurable property, and it is the property this paper sets out to measure.

Interactive planning research has tackled the conversational half of this problem. KnowNo, a system built on PaLM-E / SayCan, detects when an instruction is unclear and proactively asks the user for help. But it assumes the robot already knows what and where the objects are. Finding the object from open-vocabulary language, inside a real reconstructed scene, is a separate capability, and it is the one SaaF provides.

1.2 Two ways language fails a robot

When a request meets a scene, two different things can go wrong, and they are independent:

  1. The sentence is vague. “Hand me the bottle” has several valid targets in this room. A system that always returns its single best match will answer, confidently, with one of them. The user asked for help and received a guess.
  2. The robot’s memory is too blurry to distinguish instances. Even a precise phrase like “the left controller” fails if the stored features of two look-alike controllers have converged. This failure belongs to the representation, not to the wording.

1.3 What the memory must provide

Working backwards from the task gives four requirements. They return in §3.3 as the checklist for SaaF’s design.

  • Object-level 3D structure — a found object must be pointable, graspable, or navigable.
  • Language attached to that structure — “tart” or “green grape” must match without a fixed class list. This is what a 3D language field supplies.
  • Separability between similar instances — two controllers on a sofa are different objects, and the representation must say so.
  • An honest uncertainty signal — a vague request should produce a question, not a confident wrong answer.

Key idea

Ambiguity is not a property of the sentence. It is a relation between the sentence and the objects that exist in this room, so it can be measured — but only inside a representation that knows the room.

2 Background: 3D language fields

Three well-known ingredients combine to make a 3D language field. This chapter reviews each one in the form SaaF uses it, then shows, in an interactive figure, what the field actually stores.

2.1 Gaussian Splatting: an explicit 3D scene

What it is. A scene is stored as millions of small 3D Gaussians. Each has a position, a shape (an oriented ellipsoid), and a color. Rendering projects them onto the image plane and alpha-blends them, which is fast enough for real-time use.

Why it matters here. The representation is explicit: individual Gaussians can be edited, grouped, or annotated, and a group of Gaussians can be treated as an object. That is what makes it possible to attach language to geometry. Earlier NeRF-based representations model a scene implicitly as a continuous field; they render beautifully but are awkward to decompose into objects and slow to query.

2.2 CLIP: one space for text and images

What it is. CLIP trains an image encoder and a text encoder so that matching pairs land close together in one shared vector space. A photo of a tart and the phrase “a photo of a tart” end up as nearby vectors.

Why it matters here. Similarity in that space is a usable proxy for meaning, so a text query can act as a search key over visual features. This is what makes open-vocabulary retrieval possible: no fixed list of classes, just vectors compared with cosine similarity.

2.3 From masks to a language field

LangSplat, the baseline SaaF builds on and improves, turns the two ingredients above into a working retrieval system in four steps:

  1. Segment. SAM extracts an object mask in every input image.
  2. Embed. A CLIP feature is computed for each masked region.
  3. Compress. A small autoencoder shrinks 512-dimensional CLIP features to 3 dimensions, which is cheap to store and to render.
  4. Attach. Each Gaussian receives the compressed feature of the object it belongs to.

At query time the scene is rendered once and every pixel carries a feature; the pixels whose feature is close enough to the query vector form the answer. Storage and comparison are cheap because the features live in 3 dimensions. That same compression is the origin of the first failure mode in §3.1.

Definition

3D language field. A reconstructed 3D scene in which every spatial element carries a language feature vector, so that natural-language phrases can be located in the scene by comparing vectors. “Field” refers to the vectors existing everywhere in the reconstruction, not only at labelled objects.

3 Where the standard pipeline breaks

Both failures start from one design decision — an autoencoder trained only to reconstruct — and one design assumption — that every query deserves an answer. This chapter shows each failure in isolation, then states the requirements that follow.

3.1 Failure A: compression erases small differences

The autoencoder is optimized to reconstruct CLIP features, not to preserve the identity of objects. Any difference that costs little reconstruction error is free to vanish, and the differences between two visually similar instances are precisely the small ones. In the compressed space the instance clusters drift together; in a sofa scene with two look-alike controllers, LangSplat’s features for the two objects become close enough to cause misrecognition.

Drag the slider below to reproduce the mechanism in miniature: two well-separated clusters at 512 dimensions become one smudge at the 3 dimensions the field stores.

3.2 Failure B: every query gets an answer

Ask for “a bottle” in a scene with several bottles and a similarity-max system must choose. The decision falls to small feature differences, and those differences can flip between viewpoints or between near-identical candidates. The paper describes the outcome as unstable retrieval: sometimes the wrong object, sometimes several objects at once. The system never reports that its top candidates are effectively tied, because that information is not part of the output it produces.

3.3 The requirements, restated

Putting the two failures next to the four requirements from §1.3, a fix has to satisfy:

  • R1 — Discriminability. Similar instances stay separable after compression, not only before it.
  • R2 — Ambiguity awareness. The space itself makes visible when a phrase covers several objects, because no external classifier can know which phrases are vague in this scene.
  • R3 — Semantic fidelity. Whatever the space does to separate instances must not destroy the CLIP meaning that the language side depends on.
  • R4 — Low query cost. Whatever the fix adds must not make retrieval slower, or the robot’s responsiveness pays for it.

Key idea

Both failures are failures of the feature space, not of the architecture around it. Adding modules would not help; changing what the space is trained to do would. SaaF’s contribution is exactly that change, in two terms: one for R1 and R3, one for R2.

4 Idea 1 — make features discriminative

Keep the autoencoder. Add one term to its loss so that it is rewarded for separating instances, not only for reconstructing them. This chapter states the loss, explains what each term does, and lets you switch the terms off one at a time.

4.1 The loss

SaaF keeps CLIP and the compression architecture, and trains the autoencoder with:

ℒ = ℒlmc + λ · ℒreconst,    where    ℒlmc = ℒpos + ℒneg

Each term has a plain-language job:

  • ℒpos = 1 − a — pull views of the same object together.

    For a tracked instance with features from several frames, a is the cosine similarity between two of those features. Minimizing 1 − a drives the similarity toward 1, so all views of one object collapse to a single direction.

  • ℒneg = max(M − b, 0) — push different objects apart.

    For two features from different instances, b is their cosine similarity. The term is zero once b falls below a margin M, and otherwise pushes the similarity down. Pairs are sampled with a margin miner, so the loss spends effort on instances that are currently too close.

  • ℒreconst — keep the meaning.

    The decoder must still reproduce the original CLIP feature from the compressed one; the loss is the sum of the cosine and L2 distances between the original and reconstructed vectors. This is what stops the encoder from inventing a separated space that no longer tracks language — requirement R3.

  • λ — the balance.

    One scalar trades semantic fidelity against separation. One knob, two forces.

4.2 What the loss does to the geometry

The two metric terms work on directions, and the reconstruction term works on distances. Consider what that means for a phrase like “bottle” that genuinely refers to several instances:

  1. Pull-together aligns the views of each instance into a single direction.
  2. Push-apart fans the instances out into different directions, so their features are well separated.
  3. A phrase that spans instances cannot satisfy push-apart against all of them and must still be reconstructable. The compromise that satisfies both is to sit near the origin: short enough to stay moderately similar to every instance it covers, long enough to retain its meaning.

4.3 A stability detail: embed only the best frame

There is a second, less visible change. LangSplat embeds features from every frame, which lets occlusion and viewpoint variation leak into the field: the same Gaussian may receive slightly different features depending on which frame contributed it. SaaF keeps the tracked masks, selects for each instance the frame with the largest mask area — the best frame — and embeds features from that frame only.

This is not a detail to skip: in the ablation it adds 9.0 mIoU on its own, before any text labels exist (Table 3, §7).

Try it

In Figure 6, turn off exactly one term, look at the space, turn it back on, and repeat. The three failure pictures are distinguishable at a glance: smear (missing ℒ pos), merge (missing ℒ neg), inflation (missing ℒ reconst). The same three behaviours reappear in the ablation results.

5 Idea 2 — ambiguity as a length

The second change is supervision. Every tracked object receives about a hundred text labels, from unique names to supercategories, and the autoencoder is trained on those labels too. This chapter explains where the labels come from, why that training makes vagueness measurable, and what the measurements look like on real scenes.

5.1 Labels from tracked masks

Text is needed for two reasons: without it the space learns where images live but never links to the language side, and the specific choice of labels is what teaches the space which phrases are vague in this scene. The labels are generated automatically, in four steps:

  1. Track. SAM2 follows each object through the capture and keeps a consistent instance ID. New objects that appear later are detected by low overlap with existing tracks and added to the set.
  2. Collect frames. The frames for an instance are ranked by mask area, and several of the largest are sampled at random. Randomness avoids near-duplicate frames and stops the labels from overfitting to one view.
  3. Compose. The sampled masks are combined into a single collage per object, with the background blacked out, so the model sees several views of one instance side by side.
  4. Ask a VLM. The collage goes to a vision-language model (GPT-4o in the paper) with a system prompt that asks for shape, color, brand, and proper names, plus a second instruction to include supercategory labels. The result is roughly 100 labels per object, deliberately spanning specificity.

5.2 Why the norm encodes ambiguity

Training on these labels produces a space with an unusual property: the length of a feature vector reports how vague the concept is. Three forces combine to produce it, and Figure 6 lets you remove them one by one:

  1. Unique concepts get pushed outward. A name like “Coke” fits exactly one instance. Push-apart drives its direction away from every other instance, and length is what keeps the directions from collapsing onto each other.
  2. Ambiguous concepts cannot pick a side. “Bottle” refers to several instances at once. A long vector far from one instance would be close to another and would fight the margin; the configuration that satisfies the loss for all instances is a short vector near the origin, moderately similar to everything it covers.
  3. Reconstruction anchors the position. The decoder still has to recover the original CLIP feature from the short vector. The origin is not a graveyard; it is a dense summarization point for concepts that are true of many objects.

The consequence is a decision rule that costs nothing extra, where qcomp is the compressed query feature:

‖qcomp‖2 < μ  ⟹  ambiguous query → ask the user,    otherwise → retrieve

5.3 The measurements on real scenes

Figure 9 shows the norms the paper actually measured for two scenes and the queries used in the experiments. The pattern to read: generic terms land well inside the threshold, specific terms climb, and the ordering tracks how many objects in that scene the phrase can refer to.

5.4 Two honest notes about the measurements

The threshold is scene-relative. “Fruit” is a specific query in the bench scene, where only grapes qualify (0.53), while “apple” is ambiguous in the figurines scene, which holds two apples (0.32). Ambiguity is measured against the objects that actually exist in the room. That is the design goal, and it is also why a threshold cannot be transplanted between scenes without care.

The threshold is chosen by hand. The paper is explicit that μ must currently be set manually per environment, and that automatic calibration is future work. §8 lists this among the open problems.

Common question

Why not simply threshold the cosine similarity of the query, instead of training for a norm? A similarity threshold can say “this match is weak”, but not “this request has several good matches”. Those are different situations: a single unfamiliar object also scores modestly. The norm in this space is trained to distinguish them, because it is a property of the phrase relative to the set of instances, not of any single comparison.

6 The full method

The method has an offline half that builds the field for one scene, and an online half that answers queries and decides when answering needs help. This chapter walks through both, then follows a single request end to end with the paper’s measured numbers.

6.2 Answering a request (per query)

The online half is four steps: two single arithmetic operations, one comparison, and possibly one question to the user.

  1. Encode. The query text is embedded by CLIP and compressed by the trained encoder into qcomp.
  2. Measure. Compute ‖qcomp‖2. If it is below μ, the request is ambiguous in this scene: say so and ask for a more specific phrase.
  3. Compare. Otherwise, render the field once and compute the cosine similarity between qcomp and the compressed feature of every rendered pixel.
  4. Return. The answer is the set of pixels whose similarity exceeds τ. SaaF compares compressed features directly, so no per-pixel decoding step is needed — this is where the speed advantage over LangSplat comes from (R4).

Worked example · the bench scene

  1. Step 1

    User: “Bring me the food.” The phrase is encoded and compressed.

  2. Step 2

    The measured norm is 0.10, below μ = 0.5. Both the tart and the green grapes qualify, so the system replies: “Do you mean the tart or the green grapes?”

  3. Step 3

    User: “The green grapes.” The new query encodes to norm 1.59 — specific.

  4. Step 4

    Cosine similarity is computed per pixel; every pixel above τ is returned as the object region. The paper reports 6.3 ms average retrieval time per query on this benchmark.

7 Experimental results

The paper evaluates on two datasets with a single GPU: 3D-OVS, six small scenes with about six objects each, several of which share a supercategory, and the Figurines scene from LERF, which is denser and harder. Baselines are Lang-SAM, LERF, 3D-OVS, and LangSplat — each the strongest of its family at the time. A rendered image is segmented by comparing the query against pixel features; IoU is measured against ground-truth masks.

Reading the sofa column: LERF collapses to 27.0, LangSplat falls 5.7 points below SaaF here, and SaaF holds 95.7. That column is the direct measurement of failure A.

7.2 Ambiguity detection

Figure 9 is the evidence for the ambiguity claim: with μ = 0.5, queries that cover several objects (0.08 to 0.44) separate cleanly from queries that name one (0.53 to 1.59) across both scenes. The paper also verifies that the separation depends on training with ambiguous labels: without them, the same queries score up to 0.25 and the gap to specific queries nearly disappears.

7.4 What the numbers mean

Three readings, in order of how much they tell you about the method:

  1. Text supervision does most of the work. Going from geometry-only to specific labels jumps 37.5 points, from 50.4 to 87.9. Without language in the training loop, the compressed space is simply not aligned with phrases.
  2. Ambiguity awareness alone slightly hurts retrieval. Adding ambiguous labels without best-frame selection costs 1.5 points (87.9 to 86.4), because margin pressure from vague concepts pulls instance features toward the origin. This is the honest cost of the second idea.
  3. Combined, the two mechanisms pay off. Best frames stabilize the per-instance features, and ambiguity labels then add 8.5 points over the label-only result, reaching 96.4. Neither component alone gets near it.

From the paper

“When training with multiple ambiguous text labels, the mIoU accuracy slightly decreased 1.5 points to 86.4%. In contrast, combining ambiguous text labels with best frame selection led to a significant improvement of 8.5 points, achieving an mIoU of 96.4%.”

8 Limitations & open problems

The paper is explicit about what it does not solve. This chapter collects the limitations, answers two practical questions, and closes with what the method contributes beyond its own numbers.

8.1 Limitations the paper names

  • Tracking is the floor. Everything depends on SAM2’s masks and instance IDs. If one physical object is split into two identities, both feature clusters collapse toward the origin, and the object may never be retrieved because it always looks ambiguous.
  • No part hierarchy. The field knows objects, not “the lid of the tart box”. Related work models whole-part-subpart relationships; SaaF does not yet, so queries that address parts fall outside what the space was trained for.
  • μ is hand-tuned per scene. The ambiguity threshold must currently be chosen manually for each environment. Real deployments need it calibrated automatically.
  • Two indoor datasets. The evaluation covers 3D-OVS and the LERF Figurines scene. Real service-robot environments with motion, changing lighting, and clutter remain future work, which the paper states as its next step.

8.2 A practical question

Common question

Is the field general, or does it need training per room? Training is scene-specific by design: the autoencoder is trained on the tracked masks and labels of one capture, which is what lets it know which phrases are vague here. The per-scene cost is one training pass plus splatting on a single consumer-grade-at-the-time GPU; the payoff is a space that reflects the actual objects in the room.

8.3 What to remember

  • The fix is in the loss, not the architecture. A metric-learning term added to a plain autoencoder solved instance discriminability; no modules were added anywhere else.
  • Ambiguity can be learned as geometry. Because vague concepts genuinely belong to several instances, they settle near the origin, and the vector’s length becomes the uncertainty signal — no separate classifier, one L2 norm per query.
  • Supervision can be generated. A VLM plus object tracking produced the ≈100 labels per object that gave the space its semantics, with no human annotation of the scene.
  • Asking beats guessing. The interaction loop turns unstable retrieval into a dialogue, at a cost of one norm and a question.

“Experimental results indicate SaaF can compute ambiguity and retrieve an object simultaneously in scenarios containing ambiguity… more practical service robots that account for ambiguity.”
